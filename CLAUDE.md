# CLAUDE.md — uwb-cat-radar

## Что это за проект

UWB-радар для отслеживания положения кота в помещении.
Аппаратная база: 9 плат **DWM1001-DEV** (nRF52832 + DW1000).
Заводская прошивка PANS не используется — пишется собственная.

Архитектура: несколько **якорей** (anchors) с фиксированным положением
+ **тег** (tag) на ошейнике. Дальности измеряются через two-way ranging,
положение вычисляется трилатерацией.

## Технический стек — КРИТИЧНО

- **Zephyr 4.4.0**, nRF Connect SDK 1.0.1
- Проект **out-of-tree** (не внутри дерева Zephyr, собственный `west` workspace)
- Работа с DW1000 идёт через **decadriver (API `dwt_*`)**, а НЕ через
  штатный драйвер Zephyr для DW1000.

### Частые ошибки, которых нужно избегать

1. **НЕ предлагать API штатного Zephyr-драйвера DW1000.** Используется только
   decadriver: `dwt_initialise()`, `dwt_configure()`, `dwt_starttx()`,
   `dwt_rxenable()`, `dwt_readrxdata()`, `dwt_setrxtimeout()` и т.д.
2. **НЕ модифицировать исходники decadriver.** Это внешний вендорский код.
   Вся логика — в обвязке проекта.
3. **НЕ переписывать структуру out-of-tree проекта** под in-tree Zephyr sample.
4. При работе со временем DW1000 помнить про единицы: device time units
   (~15.65 ps), а не микросекунды. Все расчёты дальности идут в DTU.

## Архитектура кода

Роль узла (initiator/responder) выбирается в **Kconfig** (`Kconfig`,
`CONFIG_UWB_ROLE_INITIATOR` / `CONFIG_UWB_ROLE_RESPONDER`), не в рантайме —
это две разные сборки в двух build-директориях (см. ниже).

Поток при старте (`src/main.c`):
1. `deca_port_init()` + `reset_DW1000()` — SPI/GPIO обвязка (`src/deca_port.c`).
2. SPI на медленной скорости, `dwt_initialise()`.
3. (опц.) `dump_device_info()` — печать OTP-калибровки, только пока SPI
   медленный (на 8 МГц OTP-чтения возвращают 0xFF).
4. SPI на быстрой скорости, `dwt_configure()` с фиксированными RF-параметрами
   из `src/dw1000_config.c` (обоснование каждого поля — `docs/config.md`)
   и антенной задержкой из OTP (`DW1000_ANT_DELAY`).
5. Диспетчер по роли: `run_initiator()` (`src/initiator.c`) или
   `run_responder()` (`src/responder.c`).

Транспорт кадров вынесен из ролевых циклов в `src/uwb_radio.c`
(`uwb_send()` / `uwb_receive()` — тонкая обёртка над decadriver с обработкой
таймаутов и CRC). Формат сообщений — `src/uwb_msg.h`
(`struct uwb_msg { type; seq; } __packed` — packed обязателен, как только
в кадр добавятся временные метки, будет критично).

Сейчас: initiator шлёт `MSG_POLL`, responder отвечает `MSG_RESPONSE` с тем же
`seq`; обе стороны читают `dwt_readtxtimestamplo32()` /
`dwt_readrxtimestamplo32()` и логируют сырую разницу меток. Вычисления
дальности из этих меток ещё нет — см. «Дальнейший план».

## Сборка и запуск

Роль зашивается на этапе конфигурации через `EXTRA_CONF_FILE`, поэтому у
initiator и responder отдельные build-директории:

```bash
west build -b decawave_dwm1001_dev -d build_initiator -- -DEXTRA_CONF_FILE=initiator.conf
west build -b decawave_dwm1001_dev -d build_responder -- -DEXTRA_CONF_FILE=responder.conf

west flash -d build_initiator   # или build_responder
```

Печать OTP-калибровки при старте (`CONFIG_UWB_DUMP_INFO`, см.
`docs/modules.md`) — добавить `info.conf` в список:
`-DEXTRA_CONF_FILE="initiator.conf;info.conf"`.

Вывод отладки — по **UART**, 115200 (не RTT, если не оговорено отдельно):

```bash
picocom -b 115200 /dev/ttyACM0
```

Оверлея devicetree под плату нет — `decawave_dwm1001_dev` используется как
есть, без каталога `boards/`.

## Структура репозитория

```
.
├── src/                             # исходники приложения
│   ├── main.c                       # инициализация DW1000, диспетчер роли
│   ├── deca_port.c/.h                # SPI/GPIO/reset обвязка под decadriver
│   ├── dw1000_config.c/.h            # фиксированные RF-параметры, антенная задержка
│   ├── uwb_radio.c/.h                # транспорт кадров (send/receive) поверх dwt_*
│   ├── uwb_msg.h                     # формат сообщений на воздухе
│   ├── initiator.c/.h                # роль initiator
│   └── responder.c/.h                # роль responder
├── vendor/decadriver/                # вендорский decadriver — не трогать
├── docs/
│   ├── config.md                     # обоснование каждого RF-параметра (датащит/UM)
│   ├── modules.md                    # реестр из 9 модулей: PART_ID, XTAL_TRIM, TX_POWER
│   └── dw1000-notes.md               # заметки из предыдущей bare-metal реализации
├── prj.conf                          # общая конфигурация Zephyr
├── initiator.conf / responder.conf   # EXTRA_CONF_FILE для выбора роли
├── info.conf                         # EXTRA_CONF_FILE для CONFIG_UWB_DUMP_INFO
├── Kconfig                           # UWB_ROLE_INITIATOR/RESPONDER, UWB_DUMP_INFO
└── CMakeLists.txt
```

## Правила работы

0. **Это учебный проект.** Моя цель — не готовый код, а понимание. Роль
   ассистента здесь — объясняющий юнит: перед реализацией и по ходу неё
   объяснять, *почему* так, что значит регистр/поле/формула, какие есть
   альтернативы. Не молча писать решение и не сокращать объяснение ради
   скорости — если что-то не изучено, лучше спросить, чем красиво угадать.
1. **Плана сначала, код потом.** Для любой нетривиальной задачи — сначала
   plan mode, план обсуждается, потом реализация.
2. **Всегда перепроверять свою работу** после внесения изменений.
3. **Не заявлять, что код работает, без проверки на железе.**
   Агент не может прошить плату и увидеть реальный радиообмен —
   формулировать как «должно работать, требует проверки на DWM1001».
4. Двигаться маленькими шагами: цель — понемногу каждый день,
   а не большой рефакторинг за один заход.
5. Комментарии в коде — по-английски. Общение со мной — по-русски.
